서버 Runtime 문제 해결 노트

세션 수명, 부분 송수신, MSG_RING, send buffer chunk 적재 정리

저자

배진후

1 문서 목적

이 문서는 ServerCorePortfolio와 RuntimeGame 문서에 나뉘어 있던 서버 Runtime의 핵심 문제 해결 과정을 한 문서로 모은 것입니다. 전체 아키텍처나 모듈 소개보다, 실제 구현 중 문제가 되었던 지점과 그 해결 방식을 설명하는 데 집중합니다.

다루는 주제는 네 가지입니다.

Lifecycle

세션 종료 중 뒤늦은 CQE로 발생하는 SEGFAULT/UAF 방지

Partial I/O

TCP stream 단편 수신과 partial send 재시도

Buffer

send buffer chunk에 작은 payload 여러 개를 적재하는 방식

Cross Ring

MSG_RING 기반 타 ring task 전달

3 세션 수명관리: SEGFAULT와 UAF

3.1 문제상황

대량 접속과 해제를 반복하는 스트레스 테스트에서 간헐적인 SEGFAULT가 발생했습니다. 크래시 지점은 CQE callback에서 Session 멤버에 접근하는 시점이었습니다.

원인은 애플리케이션의 세션 종료 시점과 kernel I/O 완료 시점이 일치하지 않는다는 점이었습니다. 애플리케이션은 연결이 끊긴 세션을 닫고 싶지만, kernel에는 아직 완료되지 않은 SQE가 남아 있을 수 있습니다.

대표적으로 다음 op들이 늦게 완료될 수 있습니다.

  • Multishot Recv
  • Send
  • Timeout
  • Shutdown
  • Cancel

특히 cancel은 헷갈리기 쉽습니다. cancel 요청 자체의 CQE가 왔다고 해서 cancel 대상 recv/send/timeout op의 CQE까지 모두 처리된 것은 아닙니다. cancel 요청 CQE와 target op CQE는 별개이며, 순서도 보장되지 않습니다.

3.2 해결 방식

초기 방식처럼 user_data에 Session*나 Session 내부 이벤트 멤버 주소를 넣으면, 세션이 먼저 해제된 뒤 늦은 CQE가 도착했을 때 UAF가 됩니다. 이를 피하기 위해 각 SQE마다 독립적인 heap operation context를 둡니다.

핵심 구조는 다음과 같습니다.

개념 코드 — IoEvent
class IoEvent {
public:
    EventHandlerRef Owner() const { return strong_owner_; }

    void SetStrongOwner(EventHandlerRef owner) {
        strong_owner_ = std::move(owner);
    }

    void SetAutoDelete(bool value) noexcept {
        auto_delete_ = value;
    }

    bool ShouldDeleteAfterDispatch(std::int32_t result,
                                   std::uint32_t flags) noexcept {
        if (!auto_delete_)
            return false;
        if (retain_after_dispatch_) {
            retain_after_dispatch_ = false;
            return false;
        }
        return Complete(result, flags);
    }

private:
    EventHandlerRef strong_owner_;
    bool auto_delete_{false};
    bool retain_after_dispatch_{false};
};

IoEvent는 CQE가 올 때까지 handler owner를 붙잡습니다. IoRing::Dispatch()는 user_data를 IoEvent*로 복원하고, owner에게 dispatch한 뒤 op가 끝났으면 삭제합니다.

개념 코드 — Dispatch
auto* ev = reinterpret_cast<IoEvent*>(cqe->user_data);
auto owner = ev->Owner();

if (owner) {
    keep_alive.push_back(owner);
    owner->Dispatch(ev, cqe->res, cqe->flags);
}

if (ev->ShouldDeleteAfterDispatch(cqe->res, cqe->flags)) {
    delete ev;
}

이 구조에서 세션 free 시점은 Disconnect()를 호출한 순간이 아닙니다. 세션을 strong owner로 잡고 있던 op context들이 모두 CQE를 받고 삭제된 뒤에야 자연스럽게 해제됩니다.

4 부분 수신: Provided Buffer와 Packet Reassembly

4.1 문제상황

TCP는 byte stream이므로 송신자가 한 번에 보낸 패킷이 수신자에게 같은 단위로 도착한다는 보장이 없습니다. 게임 패킷 하나가 여러 recv CQE로 나뉠 수 있고, 반대로 여러 작은 패킷이 한 번의 recv에 함께 들어올 수도 있습니다.

또 하나의 문제는 Provided Buffer 고갈입니다. 동시 접속과 수신이 몰려 Provided Buffer Ring의 버퍼가 모두 사용 중이면 kernel이 ENOBUFS를 반환할 수 있습니다. 이때 Multishot Recv가 해제되는데, 이를 감지하지 못하면 해당 세션은 수신이 멈춘 것처럼 보입니다.

4.2 해결 방식

수신 경로는 fast path와 slow path로 나눕니다.

경로 조건 처리
Fast path 하나의 provided buffer 안에 완전한 요청/패킷이 있음 span으로 직접 읽고 즉시 buffer 반환
Slow path 패킷이 여러 recv CQE로 나뉨 RecvBuffer에 복사해 완전한 패킷이 될 때까지 누적
Recovery ENOBUFS 또는 Multishot 종료 RegisterRecv()로 recv op 재등록

RuntimeGame의 PacketSession은 [size:uint16][msgId:uint16] header를 기준으로 완전한 패킷만 상위 handler로 올립니다.

중요한 점은 provided buffer를 오래 붙잡지 않는 것입니다. 상위 프로토콜 처리가 늦어져도 kernel buffer가 계속 점유되면 다른 세션의 buffer 고갈로 이어질 수 있으므로, 필요한 경우 애플리케이션 소유 RecvBuffer로 복사하고 provided buffer는 빠르게 돌려줍니다.

5 부분 송신: SendOp와 Short Write Retry

5.1 문제상황

송신도 한 번의 submit으로 끝난다고 가정할 수 없습니다. sendmsg는 요청한 byte보다 적은 byte만 보낸 뒤 완료될 수 있습니다. 이때 payload 메모리가 이미 해제되었거나, 어느 iovec까지 전송됐는지 추적하지 못하면 데이터가 깨지거나 중복 전송될 수 있습니다.

5.2 해결 방식

send op가 송신에 필요한 모든 것을 직접 소유합니다.

개념 코드 — SendOp
struct SendOp final : ring::SendEvent {
    struct msghdr msg{};
    std::vector<struct iovec> iovecs;
    std::vector<SendBufferRef> bufs;
};

SendOp이 SendBufferRef를 들고 있기 때문에 send CQE가 올 때까지 payload 메모리가 유지됩니다. partial send가 발생하면 이미 보낸 byte 수만큼 iovec의 시작 위치와 길이를 조정하고 같은 op를 다시 제출합니다.

RetainAfterDispatch()가 필요한 이유는 dispatch 중 같은 op를 재제출하기 때문입니다. 현재 CQE 처리가 끝났다고 op를 삭제하면 재제출된 SQE의 user_data가 dangling pointer가 됩니다.

6 Send Buffer Chunk 적재

6.1 문제상황

게임 패킷이나 작은 HTTP 응답은 payload 크기가 작습니다. 이런 요청마다 별도 send buffer chunk를 하나씩 할당하면 다음 문제가 생깁니다.

  • chunk 내부 남은 공간이 버려져 메모리 효율이 떨어집니다.
  • send queue에 작은 buffer 조각이 많이 쌓입니다.
  • iovec 수가 늘어나고 partial send 보정 범위가 복잡해집니다.
  • backpressure accounting에서 작은 단위가 과도하게 많아집니다.

6.2 해결 방식

작은 payload는 send buffer chunk 하나에 순차적으로 적재합니다. chunk는 실제 메모리 블록을 소유하고, 각 send 요청은 (offset, length) view로 queue에 올라갑니다.

이 방식의 기준은 다음과 같습니다.

항목 설명
write cursor chunk 안에서 다음 payload를 기록할 위치
offset/length view send queue가 참조하는 실제 송신 범위
SendBufferRef chunk 메모리를 CQE 완료까지 유지하는 참조
partial send 보정 chunk를 복사하지 않고 iovec base/len만 조정

이 구조는 작은 요청 여러 개를 하나의 메모리 chunk에 모으면서도, kernel에는 iovec 범위로 각각의 송신 구간을 전달할 수 있습니다. 따라서 payload 수명은 chunk reference가 보장하고, 재시도는 iovec view만 수정해서 처리합니다.

7 타 Ring 메시지 전달: MSG_RING

7.1 문제상황

io_uring은 ring-per-thread 모델로 구성했습니다. 세션은 accept된 ring에 종속되고, 이후 recv/send도 같은 ring에서 처리됩니다. 이 구조는 cache locality와 단순한 세션 수명관리에는 유리하지만, 다른 ring에 있는 세션으로 작업을 보내야 할 때 문제가 됩니다.

예를 들어 Room broadcast에서 Room logic은 worker A에서 실행되지만, 어떤 플레이어의 세션은 worker B의 ring에 속해 있을 수 있습니다. 이때 세션을 worker A로 옮기지 않고, worker B ring에서 안전하게 send를 실행해야 합니다.

7.2 해결 방식

IORING_OP_MSG_RING으로 target ring의 CQ에 task를 직접 삽입합니다.

핵심은 user_data의 bit 0을 task flag로 쓰는 것입니다. 일반 I/O 이벤트는 IoEvent*이고, MSG_RING task는 heap에 할당한 move_only_function<void()>* 주소에 bit 0을 세팅해 구분합니다.

개념 코드 — RunOnRing
bool IoRing::RunOnRing(std::move_only_function<void()> task) noexcept {
    if (t_current_ == this) {
        task();
        return true;
    }

    auto* task_ptr =
        new std::move_only_function<void()>(std::move(task));
    std::uint64_t tagged =
        reinterpret_cast<std::uint64_t>(task_ptr) | 0x1ULL;

    io_uring_sqe* sqe = io_uring_get_sqe(t_current_->ring_);
    io_uring_prep_msg_ring(sqe, Fd(), 0, tagged, 0);
    sqe->flags |= IOSQE_CQE_SKIP_SUCCESS;
    io_uring_submit(t_current_->ring_);
    return true;
}

target ring의 dispatch에서는 bit 0으로 일반 I/O와 task를 구분합니다.

개념 코드 — Dispatch 분기
const std::uint64_t data = cqe->user_data;

if (data & 0x1ULL) {
    auto* task =
        reinterpret_cast<std::move_only_function<void()>*>(
            data & ~0x1ULL);
    (*task)();
    delete task;
} else {
    auto* ev = reinterpret_cast<IoEvent*>(data);
    // normal I/O dispatch
}

이 방식은 세션을 다른 worker로 마이그레이션하지 않습니다. 대신 “그 세션이 속한 ring에서 실행해야 하는 일”만 target ring으로 보냅니다.

8 전체 흐름으로 다시 보기

아래 흐름은 수신, Room job, cross-ring send, partial send가 함께 얽히는 게임 서버 상황을 요약한 것입니다.

이 흐름에서 Runtime이 보장해야 하는 것은 세 가지입니다.

  1. CQE가 늦게 오더라도 Session과 buffer가 먼저 해제되지 않아야 합니다.
  2. TCP stream의 단편 수신과 partial send를 모두 정상 경로로 처리해야 합니다.
  3. 다른 ring의 세션 작업은 해당 세션이 속한 ring에서 실행되어야 합니다.

9 발표용 요약

이 Runtime에서 가장 중요하게 본 문제는 io_uring의 완료 이벤트가 애플리케이션 객체 수명보다 늦게 올 수 있다는 점입니다. 그래서 user_data에 Session*를 직접 넣지 않고, SQE마다 독립적인 op context를 두었습니다. op context는 owner와 buffer를 CQE까지 붙잡고, dispatch 후 완료 여부에 따라 자동 삭제됩니다.

수신은 Provided Buffer를 사용하지만 TCP stream 단편화 때문에 완전한 패킷만 zero-copy처럼 처리하고, 단편 패킷은 RecvBuffer에서 재조립합니다. 송신은 SendOp이 iovec과 SendBufferRef를 소유해 partial send가 나도 남은 범위만 보정해 재제출합니다. 작은 패킷은 send buffer chunk 하나에 여러 개를 적재해 메모리 낭비와 queue 조각화를 줄였습니다.

멀티스레드에서는 세션이 accept된 ring에 묶이므로, 다른 worker의 세션에 직접 접근하지 않습니다. 대신 MSG_RING으로 target ring의 CQ에 task를 넣고, 그 ring의 dispatch loop에서 send 같은 세션 작업을 실행합니다. 이 구조로 세션 수명, buffer 수명, worker 간 작업 전달을 같은 CQE 중심 모델 안에서 정리했습니다.
