수명관리

최종 구조

수명관리의 핵심은 세션 객체 하나를 누가 끝까지 소유하느냐가 아니라, 세션이 비동기 경계를 지날 때 각 구간의 생존을 누가 보장하느냐입니다. 현재 구조는 SessionManager, IoEvent.owner, IoRing::keep_alive, pending_io_가 서로 다른 경계를 담당합니다.

SessionManager

connected session의 장기 소유자

IoEvent.owner

submitted I/O callback safety의 임시 소유자

IoRing::keep_alive

current dispatch stack safety의 임시 소유자

pending_io_

connected ownership을 언제 release할지 결정하는 counter

Important핵심 관점

disconnect는 객체 파괴가 아니라 상태 전환입니다. 실제 객체 소멸은 SessionManager::Release() 이후에도 남아 있는 event owner, dispatch keep_alive, 외부 shared_ptr가 모두 사라진 뒤에 일어납니다.

소유권 이동 관점에서 보면 session은 하나의 owner가 순서대로 넘겨받는 객체가 아닙니다. 단계별로 필요한 strong owner가 추가되고, 해당 경계가 끝나면 빠집니다. Figure 1 는 상태 전환을 보여주고, Figure 2 는 각 owner가 붙는 비동기 경계를 보여줍니다.

전체 흐름은 Figure 3 처럼 accept, I/O submit, CQE dispatch, disconnect drain, release가 순서대로 이어집니다.

공통 문제: raw Session* 하나로는 경계를 표현할 수 없다

문제는 session 객체 자체보다 session이 여러 비동기 경계를 지나갈 때 발생했습니다. 초기 설계처럼 raw Session* 하나로 모든 상태를 대표하면 각 경계에서 서로 다른 수명 요구를 표현할 수 없습니다.

즉 수명관리 문제의 본질은 “세션이 살아 있는가”가 아니라 “각 비동기 경계에서 어떤 owner가 그 구간의 생존을 보장하는가”였습니다.

IoEvent.owner

IoEvent.owner는 kernel에 제출된 작업이 나중에 completion으로 돌아왔을 때 callback 대상 session이 살아 있도록 붙잡는 임시 owner입니다.

문제사항

SQE submit 이후 completion 시점은 kernel이 결정합니다. close나 disconnect가 먼저 실행되어도 이미 제출된 recv, send, timeout, cancel 작업의 CQE는 뒤늦게 도착할 수 있습니다. 이때 user_data에 raw Session*만 넣으면 CQE dispatch가 이미 해제된 객체를 접근할 수 있습니다.

cancel도 같은 이유로 단순하지 않습니다. cancel request CQE는 “cancel 요청 처리 완료”이고, target recv/send CQE는 별도로 도착합니다. 따라서 cancel CQE가 왔다고 target operation의 수명이 끝났다고 볼 수 없습니다.

multishot recv는 한 번 submit한 작업에서 여러 CQE가 발생합니다. 중간 CQE마다 작업을 끝났다고 처리하면 아직 kernel이 같은 event로 completion을 더 돌려줄 수 있는 상태에서 owner를 놓게 됩니다.

해결 원리

I/O submit 경계에서는 event가 session을 잡습니다. manager owner는 “연결 목록에 남아 있는가”를 의미하고, event owner는 “이미 kernel에 제출한 작업의 callback을 안전하게 받을 수 있는가”를 의미합니다.

auto* recv_ev = new ring::RecvEvent();
recv_ev->SetStrongOwner(shared_from_this());
recv_ev->SetAutoDelete(true);
++pending_io_;
ring_.PrepRecvMultishot(*recv_ev, Fd());

Figure 5 처럼 SQE 제출 시점에는 event owner가 session을 붙잡고, CQE dispatch 시점에는 event owner를 통해 callback 대상에 접근합니다.

multishot recv는 CQE가 여러 번 올 수 있으므로 final CQE에서만 pending count와 active event 상태를 정리합니다.

if (!more) {
    recv_armed_ = false;
    active_recv_ev_ = nullptr;
    --pending_io_;
}

IoRing::keep_alive

IoRing::keep_alive는 CQE callback이 실행되는 현재 stack frame 동안 session이 중간에 해제되지 않도록 붙잡는 dispatch owner입니다.

문제사항

IoEvent.owner가 CQE 도착까지의 생존을 보장하더라도 callback 실행 중에는 다른 일이 벌어질 수 있습니다. callback 내부에서 disconnect가 발생하거나, TryRelease()가 성공해서 SessionManager::Release()가 호출될 수 있습니다. 이 순간 event owner나 manager owner가 정리되면 현재 callback stack에서 접근 중인 session이 마지막 참조를 잃을 수 있습니다.

즉 submitted I/O 경계와 dispatch 실행 경계는 다릅니다. event owner만으로는 “callback에 들어오기 전까지”와 “callback 실행 중”을 명확히 분리해서 설명하기 어렵습니다.

해결 원리

CQE dispatch 경계에서는 keep_alive가 현재 callback stack을 보호합니다.

auto* ev = reinterpret_cast<IoEvent*>(data);
auto owner = ev->Owner();

if (owner) {
    keep_alive.push_back(owner);
    owner->Dispatch(ev, result, flags);
}

event owner는 CQE가 callback으로 들어올 수 있게 보장하고, keep_alive는 callback 실행 중 manager release나 다른 owner release가 발생해도 현재 stack frame의 Session 접근이 안전하도록 보장합니다.

SessionManager

SessionManager는 현재 연결된 session 목록을 유지하는 장기 owner입니다. 다만 submitted I/O나 dispatch stack의 생존까지 모두 책임지는 owner는 아닙니다.

문제사항

accept 직후에는 factory/local shared_ptr가 session을 임시로 들고 있습니다. 하지만 이 owner는 accept 처리 scope가 끝나면 사라집니다. 연결된 세션을 계속 유지하려면 Start() 시점에 connected session owner를 명확히 등록해야 합니다.

반대로 SessionManager owner를 너무 크게 해석해도 문제가 생깁니다. SessionManager::Release()를 객체 파괴로 이해하면, 이미 제출된 event owner나 현재 dispatch keep_alive가 남아 있는 상황을 설명할 수 없습니다. manager release는 connected owner를 놓는 일이지 destructor 호출이 아닙니다.

해결 원리

accept부터 connected owner 등록까지는 다음 흐름입니다.

Listener::OnAccept()
  -> accepted fd 수신
  -> SessionFactory로 SessionRef 생성
  -> sess->Start()

Session::Start()
  -> ring_.Sessions().Add(self)
  -> OnConnected()
  -> connected callback 호출
  -> RegisterRecv()
  -> ArmWatchdog()

Start() 이후 연결 유지 여부는 SessionManager가 결정합니다. accept 시점의 factory/local owner는 임시 owner이고, manager strong ref가 추가된 뒤 local ref는 scope 종료와 함께 사라집니다.

auto self = std::static_pointer_cast<Session>(shared_from_this());
ring_.Sessions().Add(self);
OnConnected();
RegisterRecv();
ArmWatchdog();

TryRelease()는 destructor를 호출하지 않습니다. 여기서 일어나는 일은 connected session owner 해제입니다.

pending_io_와 TryRelease()

pending_io_는 object lifetime 자체를 담당하는 owner가 아닙니다. 등록한 I/O 중 아직 최종 완료되지 않은 작업 수를 세고, disconnect notification과 manager release 타이밍을 결정하는 release gate입니다.

문제사항

disconnect는 단일 이벤트가 아니라 여러 completion이 정리되는 과정입니다. shutdown, recv cancel, timeout cancel, send completion이 서로 다른 시점에 도착할 수 있고, close flag 하나만으로는 언제 disconnect callback을 호출해도 되는지 알 수 없습니다.

또한 graceful close에서는 send queue나 app-level async work가 남아 있을 수 있습니다. 응답 전송이나 DB callback이 끝나기 전에 disconnect notification을 먼저 보내면 application이 기대하는 순서가 깨집니다.

해결 원리

등록한 작업은 submit 성공 시 pending_io_를 증가시키고, 해당 작업의 최종 CQE에서 감소시킵니다.

I/O 등록 성공
  -> pending_io_++

최종 CQE 도착
  -> pending_io_--

disconnect는 중복 실행을 막기 위해 owner ring에서 disconnecting_을 먼저 세운 뒤 shutdown과 cancel event를 등록합니다.

if (disconnecting_) return;
disconnecting_ = true;

disconnect 이후 도착하는 recv, send, timeout, cancel CQE는 새 작업을 이어가기보다 pending count를 정리하고 TryRelease()로 이어집니다. 최종 release 조건은 TryRelease()에서 확인하도록 둡니다.

if (!disconnecting_ || pending_io_ > 0)
    return;

if (disconnected_notified_)
    return;

disconnected_notified_ = true;

OnDisconnected();
on_disconnect_(self);
ring_.Sessions().Release(self);

app-level 비동기 작업은 BeginAppIo() / EndAppIo()로 drain에 포함시킵니다.

Graceful close와 worker stop

graceful close와 worker shutdown도 같은 경계 모델을 따릅니다. 둘 다 “close 요청”과 “실제 release 가능 시점”을 분리해서 처리합니다.

문제사항

graceful close에서는 send queue, active send, app-level async work가 남아 있을 수 있습니다. worker shutdown에서는 accept를 먼저 멈춰도 기존 세션의 in-flight I/O가 남아 있을 수 있습니다. 이 상태에서 worker를 바로 종료하면 CQE drain과 callback 실행이 중간에 끊깁니다.

해결 원리

Graceful close는 DisconnectAfterFlush()가 담당합니다. 즉시 shutdown하지 않고 send queue, active send, app-level async work가 모두 비워질 때까지 기다린 뒤 Disconnect()로 넘어갑니다.

Worker::Stop()은 accept를 먼저 멈추고, manager snapshot에 있는 live session에 graceful close를 요청합니다. timeout 안에 drain이 끝나지 않으면 force disconnect로 넘어갑니다.

Note텍스트로 보는 전체 흐름 
Accept
  -> factory creates shared_ptr<Session>
  -> Session::Start()

Start
  -> SessionManager::Add(session)
  -> OnConnected()
  -> RegisterRecv()
  -> optional ArmWatchdog()

  -> RecvEvent created
  -> RecvEvent.owner = session
  -> pending_io_++
  -> io_uring recv_multishot submitted

Recv CQE
  -> IoRing gets IoEvent*
  -> event.owner copied into keep_alive
  -> Session::OnRecv()
  -> if final CQE: pending_io_--

Send
  -> SendEvent/SendOp.owner = session
  -> pending_io_++
  -> completion: pending_io_--

Disconnect
  -> shutdown/cancel events registered
  -> each event owns session
  -> each final CQE decrements pending_io_

TryRelease
  -> waits until disconnecting_ && pending_io_ == 0
  -> OnDisconnected()
  -> SessionManager::Release(session)

Destruction
  -> after manager ref + event owner refs + dispatch keep_alive refs are gone
  -> Session destructor
  -> SocketHandle closes fd

결과

close 이후 늦게 도착하는 CQE도 안전하게 처리할 수 있습니다. session 해제 시점은 application close 호출이 아니라, runtime이 in-flight operation을 모두 정리하고 SessionManager에서 connected session ref를 제거한 뒤로 이동했습니다.

이 구조는 필요 이상으로 방어적인 구조라기보다, io_uring completion 모델에서 필요한 방어선을 경계별로 나눈 구조입니다.

SessionManager owns "connected session".
IoEvent owns "submitted operation callback safety".
keep_alive owns "current dispatch stack safety".
pending_io_ decides "when connected ownership can be released".

문제와 해결 과정은 모두 이 경계에서 발생합니다. accept 이후 connected owner를 등록하는 경계, SQE submit 이후 kernel이 completion을 돌려주는 경계, callback 실행 중 release가 발생할 수 있는 dispatch 경계, disconnect 이후 모든 pending work를 drain하고 manager owner를 놓는 release 경계를 각각 분리했기 때문에 UAF 없이 종료할 수 있습니다.
