9. 프레임워크를 실제 앱으로 검증

9. RuntimeWeb, RuntimeProxy, RuntimeGame으로 실제 앱 검증

1 프레임워크를 실제 앱으로 검증

프레임워크 개발이 문서 설명에 머물지 않도록 웹 서버, 프록시 서버, 게임 서버 형태의 실제 앱으로 확장한 흔적은 2026년 4월 말부터 집중적으로 나타납니다.

이 검증은 새로 만든 데모 앱을 억지로 붙인 것이 아니라, 이전부터 운영하던 Linux/Docker 기반 개인 서비스와 게임 서버 운영 경험에서 이어졌습니다. 여러 서비스를 Docker로 띄우고, 외부에서 개발 서버와 게임 서버에 접근하고, 개인 도메인과 DNS, VPN, proxy, Kubernetes ingress를 함께 다루다 보면 공통적으로 필요한 경계가 드러납니다.

운영에서 반복된 요구 런타임 검증 앱에서 확인한 것
정적 문서와 웹 서비스를 직접 제공해야 함 RuntimeWeb으로 HTTP 정적 파일 서빙과 Router를 검증
외부 요청을 안전하게 내부 서비스로 분기해야 함 RuntimeProxy로 SNI route, upstream 선택, timeout을 검증
친구들과 사용할 게임 서버처럼 상태 있는 세션을 다뤄야 함 RuntimeGame으로 패킷 프레이밍과 Room/JobQueue를 검증
느린 peer나 장애 upstream이 전체 서버를 막으면 안 됨 Core 송신 큐, backpressure, recv pause/resume 경계를 검증

1.1 검증 방식

RuntimeWeb은 정적 문서와 포트폴리오 페이지를 제공하는 웹 서버 경로로 검증되었습니다. RuntimeProxy는 외부 HTTPS 요청이 들어왔을 때 SNI와 route tree를 기준으로 upstream을 선택하는 프록시 경로로 검증되었습니다. RuntimeGame은 TCP stream 위에서 패킷 경계를 복원하고 Room 단위로 상태 변경을 직렬화하는 게임 서버 경로로 검증되었습니다.

현재 dashboard/src/DevOpsInlinePortfolio.jsx에는 다음 근거가 남아 있습니다.

파일 위치 근거
destinationLabels Docker / local, Kubernetes ingress, Kubernetes API HA 같은 upstream 분류
RouteTopologyFlow edge proxy에서 destination별 route를 시각화
traffic path rows Client, Home Router, Edge Mini PC, Runtime Proxy, SNI Route, Ingress, Workload 순서
summary copy C++ io_uring 서버 런타임 위에 웹 서버와 HTTPS reverse proxy를 구현했다는 설명

1.2 포트폴리오 문장으로 정리

게임 서버용으로 시작한 io_uring 기반 Core 런타임을 HTTP 정적 파일 서빙과 HTTPS reverse proxy 경로로 확장했습니다.
외부 요청은 개인 도메인과 SNI route를 통해 RuntimeProxy에 들어오고, RuntimeProxy는 Docker/local service,
RuntimeWeb, Kubernetes ingress 중 실제 upstream으로 분기하도록 구성했습니다.

이 구조는 이전부터 Docker 서비스와 게임 서버를 직접 운영하면서 겪은 요구를 프레임워크 검증 대상으로 바꾼 것입니다.
웹 서비스는 RuntimeWeb으로, 외부 진입 경로와 장애 격리는 RuntimeProxy로, 상태 있는 게임 세션은 RuntimeGame으로 나누어
Core 런타임의 수명주기, 버퍼, 송신 순서, backpressure 규칙을 실제 사용 경로에서 확인했습니다.
