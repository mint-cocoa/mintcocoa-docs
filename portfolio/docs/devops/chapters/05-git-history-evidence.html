5. Git 이력으로 확인한 운영 구조 변화

mintcocoa-ops 원격 로그에서 확인되는 production GitOps 전환 흐름

1 확인한 기준

이 장은 mintcocoa-ops 원격 origin/main의 Git 로그를 근거로 작성했습니다. 로컬 작업트리는 원격보다 뒤에 있을 수 있으므로, 문서 작성 기준은 fetch 이후의 origin/main입니다.

git -C /home/cocoa/mintcocoa-ops fetch origin main --prune
git -C /home/cocoa/mintcocoa-ops log --date=short --pretty=format:'%h %ad %s' origin/main --max-count=35

3 재작성 커밋의 의미

85018d9는 파일 수 기준으로도 큰 전환점입니다. 기존 cloud, Gateway API, Ansible, 일부 Terraform scaffold를 걷어내고, OKE production root와 observability application, runbook 중심으로 저장소를 다시 구성했습니다.

이 커밋 이후 운영 저장소는 “여러 실험을 담은 ops repo”보다 “OKE production desired state를 선언하는 repo”에 가깝게 바뀌었습니다.

이전 성격 이후 성격
cloud/home 실험과 scaffold 혼재 OKE production first
여러 migration report와 diagram 산재 current-state, operations, runbook 중심
앱별 manifest 경계가 불명확 apps/<app>/base와 overlay 구조
외부 접근 경로가 여러 후보로 남음 public ingress, private ingress, operator path 경계 분리

4 application 추가 흐름

whoami는 pipeline proof 역할로 남고, dropapp은 실제 RuntimeWeb workload로 추가되었습니다. 이후 mintcocoa-docs가 별도 OKE app으로 들어오면서 이 문서 사이트 자체도 production GitOps 경로의 사례가 되었습니다.

앱 이력에서 확인한 역할
whoami home과 OKE overlay 구조를 검증하는 proof service
dropapp RuntimeWeb 기반 공개 앱, home 검증 후 OKE Ingress 공개
mintcocoa-docs 문서 사이트 자체를 OKE production에서 서빙하는 앱

5 운영 제약이 드러난 커밋

dropapp OKE 배포 이력에는 앱 코드와 클러스터 실행 환경 사이의 제약이 드러납니다. d98fc1c는 OKE overlay에 seccompProfile: Unconfined를 적용해 io_uring 실행 조건을 맞췄습니다.

관측성 이력에서는 storage 비용과 footprint를 줄이는 방향이 보입니다. b27e056, b5c18bd, 33ec9e8, 7530cc2는 paid resource와 persistent storage를 줄이고 Loki writable path와 ephemeral profile을 정리한 흐름입니다.
