# Git 이력으로 보는 전체 개발 흐름

이 장들은 구현 포트폴리오를 보조하는 증명용 문서입니다. 단순히 어떤 기술을 사용했다고 나열하기보다, 저장소의 커밋 이력과 현재 남아 있는 파일을 기준으로 어떤 흐름으로 작업 범위가 확장되었는지 정리합니다.

초기 저장소는 인프라 포트폴리오가 아니라 게임 서버, 게임 클라이언트, 그래픽스 설계, 자기소개/지원 문서, 공개 페이지 산출물을 함께 담은 포트폴리오 저장소였습니다. 다만 개발 흐름의 배경에는 이전부터 Linux와 웹 서비스 운영에 관심을 두고 Docker 위에 여러 서비스를 띄우거나, 친구들과 함께 사용할 게임 서버를 직접 구성해 본 경험이 있었습니다. 이후 포트폴리오 저장소는 GitHub Pages 중심으로 정리되고, 서버 런타임 검증 앱, 운영 대시보드, CI/CD, GitOps, 홈랩 인프라, 홈페이지, Quarto 출판 파이프라인으로 확장되었습니다.

단, 아래 타임라인의 상세 커밋은 `portfolio-head` 저장소 안의 Git 이력입니다. 인증된 GitHub 조회 기준으로 `mint-cocoa` 계정에는 2026-06-08 현재 124개 저장소가 보이며, 이 중 fork가 아닌 저장소는 106개, archive되지 않은 owner 저장소는 64개입니다. 따라서 2026년 4월 이후의 포트폴리오 커밋만으로 전체 개발 이력을 설명하면 범위가 좁아집니다. 이 문서는 GitHub 계정 전체의 저장소 생성 흐름과 현재 `portfolio` 저장소의 파일/커밋 증거를 함께 묶습니다.

## 개발자로서의 변화

초기 작업은 웹 프레임워크와 API를 익히는 단계에 가까웠습니다. 동시에 개인 Linux 환경에서 Docker 서비스들을 띄우고, 게임 서버나 개발 서버를 외부에서 안정적으로 접근할 수 있게 만드는 운영 문제에도 관심이 있었습니다. 이 과정에서 단순히 애플리케이션을 작성하는 것만으로는 충분하지 않고, 네트워크 경로, 배포 일관성, 저장소와 파일 관리, 장애 시 우회 경로까지 함께 설계해야 한다는 점을 경험했습니다.

이후 MSA와 Kubernetes를 다루면서 서비스가 배포되고 관측되는 방식을 고민하기 시작했고, 2025년부터는 TCP 서버와 게임 서버 구현으로 관심사가 네트워크 런타임 내부로 내려갔습니다.

2026년의 핵심 변화는 문제의 단위가 기능 구현에서 실행 모델 설계로 바뀌었다는 점입니다. 단순히 요청을 처리하는 서버가 아니라, 비동기 I/O 완료가 늦게 돌아오고, 세션 종료와 송신 재시도가 겹치며, 버퍼와 이벤트의 수명이 서로 다른 상황을 어떻게 안전하게 정리할 것인지가 중심 문제가 되었습니다. 즉, 예전부터 직접 운영하던 웹 서비스와 게임 서버의 요구가 C++ 서버 런타임 구현으로 내려갔고, 다시 그 런타임을 실제 Web/Proxy/Game 앱과 홈랩 배포 경로로 검증하는 흐름이 되었습니다.

따라서 현재 포트폴리오의 주력 서사는 다음과 같이 정리됩니다.

```text
웹/백엔드 기초
-> Linux/Docker 기반 개인 서비스 운영
-> Python API와 MSA/Kubernetes
-> TCP 서버와 게임 서버 실험
-> C++ ServerCore와 io_uring 런타임
-> Web/Proxy/Game 실제 앱 검증
-> Proxmox/NAS/VPN/DNS/Proxy/GitOps 운영 구조
-> Quarto/PDF 출판
```

이 흐름은 여러 기술을 흩어서 사용했다는 의미가 아닙니다. 점점 더 낮은 레벨의 서버 실행 기반으로 내려간 뒤, 다시 그 결과를 운영과 문서 출판까지 끌어올린 과정입니다.

현재 개발자 정체성은 C++ 기반 고성능 게임 서버/runtime 개발을 중심으로, Linux 네트워크 I/O, Kubernetes/GitOps 운영, 문서화된 포트폴리오 출판까지 연결하는 시스템 지향 백엔드 개발자에 가깝습니다.

## 운영 경험을 전제로 한 재구성

이 포트폴리오의 운영 축은 나중에 붙인 장식이 아니라 프레임워크 개발의 검증 요구에서 출발합니다. 이전부터 Linux 위에서 Docker 서비스들을 실행하고, 친구들과 함께 사용할 게임 서버를 구성하면서 다음과 같은 문제가 반복되었습니다.

| 운영 문제 | 해결 방향 | 포트폴리오에서 이어진 작업 |
| --- | --- | --- |
| 여러 개발 환경에서 빌드와 배포 결과가 달라짐 | GitHub Actions 기반 CI와 container image 빌드 | `.github/workflows/portfolio-image.yml`, GHCR image, GitOps image tag 갱신 |
| 개인 서버의 파일과 상태를 안정적으로 관리해야 함 | Proxmox 위 VM과 NAS 서비스, NFS/PV 백업 scaffold | Proxmox/Prometheus 운영 API, NFS PV backup CronJob |
| 외부에서 개발 서버나 게임 서버에 안전하게 접근해야 함 | Tailscale VPN, 개인 도메인, Cloudflare DNS | 외부 접근 경로와 route tree를 런타임 문서에 반영 |
| 홈 네트워크 장애나 단일 진입점 장애를 줄여야 함 | Oracle Cloud VM을 프록시/로드밸런싱 경계로 사용 | RuntimeProxy, SNI route, upstream 분기 모델 |
| 인프라 설정을 수동 기록으로만 남기기 어려움 | Terraform, Helm chart, GitOps repo로 desired state 관리 | `home-k8s-gitops`, `mintcocoa-ops`, Terraform/Ansible/Kubespray scaffold |

따라서 `ServerCore`는 추상적인 프레임워크 실험으로만 작성된 것이 아닙니다. 직접 운영하던 웹 서비스와 게임 서버에서 필요했던 연결 수락, 프록시, 정적 파일 서빙, route 분기, 배포 일관성, 관측 가능성을 실제 검증 대상으로 삼기 위해 `RuntimeWeb`, `RuntimeProxy`, `RuntimeGame`, 운영 대시보드, GitOps 배포 흐름으로 확장되었습니다.

## 전체 이력 확인 명령

```powershell
git log --all --reverse --date=short --pretty=format:"%h`t%ad`t%s"
```

파일 단위 변화까지 함께 보려면 다음 명령을 사용합니다.

```powershell
git log --all --reverse --date=short --pretty=format:"COMMIT%x09%h%x09%ad%x09%s" --name-status
```

DevOps, 배포, 인프라 관련 이력만 좁혀 보려면 다음 명령을 사용할 수 있습니다.

