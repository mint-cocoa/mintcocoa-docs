## 선택 모듈로 확장한 결과

최종 구조에서 Core 런타임은 특정 서버 제품이 아니라 프로토콜에 종속되지 않는 TCP 전송 계층입니다. Core는 소켓 수락, 세션 수명주기, 수신/송신, 제공 버퍼, 송신 큐, 타임아웃, worker-owned ring, CQE 기반 완료 처리 같은 공통 I/O 책임을 맡습니다. HTTP 요청 해석, 프록시 라우팅, 게임 패킷 프레이밍과 Room 실행 모델은 Core 밖의 선택 모듈이 담당합니다.

## 모듈별 검증

### `iouring::http`

`iouring::http`는 Core `Session::OnRecv()`로 올라온 TCP 바이트를 HTTP/1.1 요청으로 해석합니다. `HttpSession`은 `HttpParser`를 통해 요청 헤더와 본문을 처리하고, `Router`에서 handler를 찾은 뒤, `HttpResponse`가 만든 응답 버퍼를 Core 송신 큐로 넘깁니다.

| 검증 항목 | 확인한 것 |
| --- | --- |
| HTTP 파서와 요청 수명주기 | TCP 스트림을 HTTP 요청 단위로 해석하고 요청 진행 상태를 관리 |
| Router / RadixTree | method, 정적 경로, parameter, wildcard route 분리 |
| 파일/본문 스트리밍 응답 | 큰 응답을 하나의 앱 메모리 버퍼에 누적하지 않고 chunk 단위로 송신 |
| timeout/backpressure 연결 | 요청 타임아웃과 송신 압력을 Core 세션 경로에 연결 |

### `iouring::stream`

`iouring::stream`은 downstream 세션과 upstream 세션을 하나의 중계 경로로 묶습니다. HTTP 요청/응답 객체를 만들지 않고, 한쪽 peer에서 받은 바이트를 반대편 peer의 송신 큐로 전달합니다.

| 검증 항목 | 확인한 것 |
| --- | --- |
| downstream/upstream 중계 | 두 TCP 세션 사이의 바이트 전달 |
| 논블로킹 연결기 | upstream 연결 타임아웃과 실패 처리 |
| TLS/SNI 라우팅 | downstream TLS 처리와 SNI 기반 upstream 선택을 stream 모듈 경계에 격리 |
| 느린 peer 처리 | write pressure를 반대편 recv pause/resume 또는 종료 정책으로 전파 |
| 운영 보조 기능 | ACME HTTP-01 challenge와 metrics snapshot을 proxy 모듈 안에 배치 |

### `iouring::game`

`iouring::game`은 게임 도메인 전체가 아니라 바이너리 패킷 프레이밍과 Room 실행 모델을 제공합니다. `PacketSession`은 `[size:uint16][msgId:uint16][payload]` 형식의 패킷 경계를 TCP 스트림 위에서 복원하고, 완전한 패킷이 만들어졌을 때만 게임 핸들러로 넘깁니다.

| 검증 항목 | 확인한 것 |
| --- | --- |
| `PacketSession` | TCP 스트림 위 바이너리 패킷 경계 복원 |
| `PacketBuilder` | payload 앞에 패킷 헤더를 붙여 Core 송신 큐로 전달 |
| `Room` / `JobQueue` | Room 상태 변경을 직렬 실행하고 Room 간 분산 허용 |
| `RoomManager` / `PlayerRegistry` | Room 수명주기와 player-session 관계 관리 |

## 결론

처음에는 서버의 연결 수락, 수신, 송신, 연결 종료 흐름을 직접 구현하는 문제로 시작했습니다. 하지만 구현이 진행될수록 핵심은 빠르게 I/O를 제출하는 코드가 아니라, 완료 통지가 늦게 도착하고, 버퍼 수명이 엇갈리고, 연결 종료 중 새 작업이 들어오고, 여러 worker가 세션이나 Room 상태를 동시에 건드릴 수 있는 상황을 끝까지 안전하게 마무리하는 데 있다는 점이 드러났습니다.

그래서 최종 구조에서 Core는 프로토콜을 모르는 상태로 남겨 두었습니다. HTTP 요청, 프록시 라우팅, 게임 패킷의 의미는 각 선택 모듈이 해석하고, Core는 세션 I/O 상태를 worker-owned ring과 세션 수명주기 규칙 안에서 처리합니다. 제출된 I/O는 CQE가 돌아올 때까지 생존해야 하고, 연결 종료는 즉시 해제가 아니라 남은 완료와 송신 상태를 정리한 뒤 확정되는 상태 전환으로 다뤄집니다. 송신 큐 역시 무제한 버퍼가 아니라 watermark, 수신 일시 정지, 연결 종료 정책을 판단하는 기준으로 사용됩니다.

결과적으로 이 구현은 단순히 빠른 서버를 만드는 작업이 아니라 완료 통지 기반 전송 런타임을 세우는 작업에 가까웠고 수명, 버퍼, 흐름, 동시성의 규칙을 고정하고, `iouring::http`, `iouring::stream`, `iouring::game`은 그 위에서 각자 프로토콜을 해석하도록 해 같은 런타임을 HTTP 서버, TCP reverse proxy, 패킷 기반 게임 서버로 확장할 수 있었습니다.
